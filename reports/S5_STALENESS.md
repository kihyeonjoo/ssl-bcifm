# 도메인 평균의 낡음(staleness): 측정, 갱신 시도, 그리고 미해결

> ⚠ **이 보고서의 transductive 수치는 참고용이며 논문 수치가 아니다.**
> 평가 데이터를 미리 본 값이 섞여 있다. 인용할 최종 값은
> [S13_FINAL_LADDER.md](S13_FINAL_LADDER.md) 와 `results/final_tables.csv` 다.

2026-09-25. 파일럿 로그 `pilot_dc.log` (50 epoch, 갱신 없음), `pilot2_dc.log`
(50 epoch, epoch당 2회 갱신 + 평가 직전 테이블), `stale_full.log` (10 epoch, 전체 학습셋 프로브).
학습 코드 변경은 [finetune_labram_hemi_aux.py](../finetune_labram_hemi_aux.py).

## 왜 쟀나

학습 중 도메인 중심화는 각 (피험자, 세션)의 CLS 평균 μ 를 빼고 head 에 넣는다. μ 는
에폭 시작에 라벨 없는 전체 패스로 계산한다. EMA 를 배제한 근거는 2 epoch 스모크에서
**에폭 간 이동량 38.0 > 평균 크기 36.4** 였다.

**그 근거는 스냅샷 방식에도 그대로 적용된다.** 스냅샷도 에폭이 진행될수록 낡는다.
그리고 그 측정에는 두 결함이 있었다 — warmup 구간이었고, **모든 도메인이 함께 움직이는
공통 이동과 도메인 간 상대 위치 변화를 구분하지 않았다.** 머리 입장에서 공통 이동은
빼기에서 상쇄되므로, 문제가 되는 것은 상대 이동뿐이다.

## 1. 측정 결과 — 낡음은 실재하고, 하필 쓰이는 시점에 가장 크다

`|rel|` 은 각 도메인 평균에서 전체 도메인 평균을 뺀 **상대 오프셋**의 크기.
`mid`/`end` 는 에폭 중간·끝에 **고정된 창**으로 다시 잰 상대 오프셋이 에폭 시작
스냅샷에서 벗어난 정도 (백분율은 `|rel|` 대비).

**낡음은 학습 후반에 사라진다** (epoch 40 이후 14% → 1%). 코사인 LR 이 0 으로 가며 모델이

> 계산한 값이었다. 전체 구간 평균(epoch 10~40)은 **38.0%** 이고, 뒤로 갈수록 급감한다.

**그런데 모델 선택은 epoch 6~10 에서 일어난다** (A팔 중앙값 7, 파일럿 6과 10).
그 구간의 낡음이 **41~55% 로 가장 크다.** 낡음은 하필 실제로 쓰이는 시점에 최대다.

### 측정 자체가 믿을 만한가 — 그렇다

64창/도메인 프로브는 그 자체로 잡음이 있다. 전체 학습셋(30,312창)으로 다시 쟀다.
LR 스케줄이 동일한 구간(epoch 1~5)만 비교 가능하다(10 epoch 실행은 코사인 총 길이가
달라 이후 구간의 LR 이 다르다).

| 1 | 101.4 | 94.2 | +7.2 |

**과대평가 폭은 end 기준 +3.2pp 에 그친다. 40% 는 측정 잡음이 아니라 실제 드리프트다.**

## 2. 갱신 시도 — 듣지 않았다

### 먼저: 샘플 갱신은 쓸 수 없다

명세의 "K 스텝마다 도메인당 샘플 창으로 갱신" 을 구현하기 전에 샘플 평균의 잡음을 쟀다
(fold 1 학습 도메인 36개, `|rel|`=11.39, 20회 반복).

| M (도메인당) | 잡음 | `\|rel\|` 대비 | 1회 비용 |
|---|---|---|---|
| 32 | 10.99 | 96.5% | 0.49초 |
| **64** | 7.27 | **63.9%** | 0.97초 |
| 128 | 4.95 | 43.4% | 1.95초 |
| 256 | 3.23 | 28.3% | 3.89초 |
| 512 | 1.74 | 15.3% | 7.78초 |
| 전체 (842) | 0 | 0% | 12.80초 |

(창 1개 forward = 0.422 ms, 실측 16초/37,890창)

**M=64 로 갱신하면 낡음 40% 를 잡음 64% 로 바꾼다.** 낡음보다 작으려면 M≥256 이어야
하는데, M=256 을 4회 갱신하면 15.6초로 **전체 패스 2회(25.6초)에 근접**하면서 28% 잡음이
남는다. **정확도가 충분한 샘플 갱신은 전체 패스보다 비싸다.**

→ 전체 패스를 K 스텝마다 돌리는 쪽으로 구현했다 (`center_refresh_windows: 0`).

### 결과: 낡음이 그대로다

`center_refresh_steps: 237` (473 스텝/epoch 이므로 epoch당 2회) + `center_fresh_eval: true`.

| epoch 10~40 평균 | mid (절반) | end (전체) |
|---|---|---|
| 갱신 없음 | 34.6% | **38.0%** |
| epoch당 2회 갱신 | 33.9% | **38.2%** |

**사실상 동일하다.** 두 가지가 겹쳤다.

**(a) 진단 지표가 갱신 후를 재지 못한다.** `[stale]` 은 "에폭 시작 스냅샷 대비 드리프트"
를 재는데, 갱신은 **모델의 드리프트 자체를 바꾸지 않는다.** 지표를 "마지막 갱신 이후
드리프트" 로 바꿨어야 했다. 설계 실수다.

**(b) 바꿔 재도 소용없다는 것이 기존 데이터로 나온다.**

```
mid/end = 0.91        (mid = 237스텝 드리프트, end = 473스텝 드리프트)
```

드리프트가 스텝 수에 비례하면 0.50 이어야 한다. **0.91 이라는 것은 드리프트가 에폭
앞부분에 몰려 있고 금세 포화한다는 뜻이다.** 갱신 주기를 절반으로 줄여도 낡음은
42% → 36%, **약 6pp 만** 내려간다. 10% 아래로 가려면 갱신을 수십 배 늘려야 하고 비용이
감당되지 않는다.

**명세의 판정 기준(10% 미만)은 합리적 비용 안에서 달성 불가능하다.**

## 3. 성능 — 갱신이 도움이 된다는 증거는 없다

fold 1, seed 0 만. **피험자 1명이므로 결론이 아니다.**

| | 선택 epoch | window | clip |
|---|---|---|---|
| A팔 S1 (학습 중 중심화 없음) | 16 | 0.5891 | 0.6222 |
| **파일럿 1** (갱신 없음) | 6 | **0.6572** | **0.8222** |
| 파일럿 2 (2회 갱신 + fresh eval) | 10 | 0.6235 | 0.6889 |

갱신을 넣은 쪽이 오히려 낮다. 선택 epoch 도 다르고 n=1 이라 잡음일 수 있다.

### prototype 경로 (파일럿 1 체크포인트)

| | 조건1 (중심화 없음) | 조건2 (head+중심화) | 조건3 (proto, 중심화 없음) | 조건4 (proto+중심화) |
|---|---|---|---|---|
| clip, 파일럿 1 | 0.5333 | **0.8000** | 0.5333 | 0.7556 |
| clip, A팔 S1 | 0.6074 | 0.7630 | 0.6148 | 0.7556 |
| win, 파일럿 1 | 0.5297 | **0.6540** | 0.5420 | 0.6544 |
| win, A팔 S1 | 0.5735 | 0.6334 | 0.5775 | 0.6324 |

- **head 경로가 올랐다** (clip 0.7630 → 0.8000). 학습 중 중심화가 head 를 중심화된 분포에
  맞춘 효과로 보인다.
- **prototype 경로는 clip 에서 동일**(0.7556). head 를 거치지 않으므로 영향이 작다.
- **조건1 이 내려갔다** (0.6074 → 0.5333). 당연하다 — 학습 중 중심화된 head 를 중심화
  없이 채점하면 분포가 어긋난다. **학습 중 중심화 모델은 평가 시에도 중심화가 필수다.**

역할별 정렬은 A팔과 같은 구조다: 학습 0.9852 / 검증 0.8222 / 테스트 0.7778
(A팔 0.9612 / 0.7988 / 0.7551).

## 4. 구현

| 설정 키 | 기본 | 뜻 |
|---|---|---|
| `domain_center` | false | 학습 중 중심화. **false 는 A팔과 bit 동일**(검증됨) |
| `center_refresh_steps` | 0 | K 스텝마다 학습 테이블 갱신 (0 = 에폭 시작만) |
| `center_refresh_windows` | 0 | 도메인당 창 수 (**0 = 전체**) |
| `center_fresh_eval` | false | val/test 테이블을 **평가 직전** 계산 |
| `center_diag` | false | 낡음 진단 로그 |
| `center_diag_windows` | 64 | 진단 프로브 창 수 (0 = 전체) |

`center_fresh_eval` 을 넣은 이유: 원래 코드는 val/test 테이블을 **에폭 시작**에 계산하는데
평가는 **에폭 끝**에 한다. 비교 대상인 오프라인 0.7180 은 채점하는 바로 그 가중치로 평균을
냈으므로, 고치지 않으면 불공정한 비교가 된다. 비용 2.5초.

도메인 평균은 **stop-gradient** 다. `domain_mean_table` 이 `@torch.no_grad()` 아래 있어
반환 텐서가 `requires_grad=False`, `grad_fn=None` 이고 `cls - center` 에서 상수로 취급된다.
텐서로 직접 확인했다.

### 비용 (실측)

| | epoch | fold(50 epoch) | 45회 |
|---|---|---|---|
| A팔 (중심화 없음) | 34초 | 33분 | 24.8시간 |

## 5. 미해결 — 낡음의 **영향**을 한 번도 재지 않았다

이 조사는 낡음의 **크기**만 쟀다. 40% 가 정확도를 얼마나 바꾸는지는 모른다.
갱신이 효과가 없었던 것도 "낡음이 무해해서" 인지 "갱신이 낡음을 못 줄여서" 인지
구분되지 않는다(§2 에 따르면 후자이지만, 그렇다면 전자는 여전히 미검정이다).

**직접 검정할 수 있다.** 같은 체크포인트를 두 방식으로 채점하면 된다.

- 낡은 테이블: 그 에폭 시작의 가중치로 만든 μ
- 신선한 테이블: 채점하는 바로 그 가중치로 만든 μ

차이가 작으면 갱신은 불필요하고, 크면 갱신 방식을 다시 설계해야 한다. 파일럿 체크포인트로
약 10분이면 된다. **이것이 A(갱신 없음)와 B(갱신)를 가르는 유일한 근거다.**
